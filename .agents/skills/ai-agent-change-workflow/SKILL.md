# AI Agent Service 변경 워크플로

프로젝트 경계와 실행·위임 정책은 [AGENTS.md](../../../AGENTS.md)를 따른다. 사용자 요청과 현재 세션의 권한을 확대하지 않는다.

## 시작 판단

1. 현재 동작, 기대 동작, 대상·제외 범위와 관측 가능한 완료 조건을 입력·응답 예시 또는 기존 테스트로 정리한다.
2. `Controller → InferenceService → 실제 AI 또는 testMode → ResultValidator`에서 실제 영향 경로를 확인한다. 클래스 이름만으로 호출 여부를 추측하지 않는다.
3. 최종 승인, 공통 근거·단위 검증, 인증, AI 입력·외부 전송, 재추론 변경은 높은 위험 후보로 보고, 실패 시 결과와 회귀 범위를 구현 전에 정한다. 위험도는 파일 수가 아니라 승인·비용·외부 전송·복구 난이도로 판단한다.
4. 작은 변경은 한 기능의 문서 또는 국소 코드 1~2개에 한정되고 API·Schema·프롬프트 계약, 최종 승인, 보안, 외부 전송·비용, 공통 검증에 영향이 없을 때만 판정한다. 해당 조건을 벗어나면 중간 이상으로 보고 요구사항·영향 분석·테스트·교차 검토 근거를 각각 남긴다. 고위험이면 구현 전 실패 시 응답, 회귀 범위, 안전한 검증 방법까지 정한다.
5. 동작이 바뀌지 않는 후속 문구·링크·포맷 수정은 원래 작업의 위험도와 관계없이 좁은 검증과 단일 후속 보고서로 끝낼 수 있다. 동작이나 외부 계약이 바뀌면 다시 위험을 판정한다.
6. 역할 문서는 해당 역할을 수행할 때만 읽는다. 단계마다 에이전트를 기계적으로 생성하지 않는다. 위임 판단과 메인 책임은 `AGENTS.md` 5절을 따른다. 변경 규모에 따른 보고서 파일명은 [보고서 규칙](../../../docs/report/report-guide.md)을 따른다.

- [요구사항 정의](../../../docs/agents/requirements-definition.md): 계약과 완료 조건을 정할 때
- [영향 분석](../../../docs/agents/impact-analysis.md): 실행 경로와 회귀 범위를 정할 때
- [구현](../../../docs/agents/implementation.md): 변경할 때
- [테스트 검증](../../../docs/agents/test-verification.md): 관측 가능한 결과를 확인할 때
- [교차 리뷰](../../../docs/agents/cross-review.md): 누락과 회귀 가능성을 검토할 때

## 변경 유형별 확인

| 변경 | 함께 확인할 범위 |
|---|---|
| DTO·API | 입력 보정, Bean Validation, 오류 HTTP 상태, API 문서·예제·화면 요청 |
| 최종 판정·검증 | certain, 전체·개별 confidence, 반려 제안, 빈 결과, 단위·단품 조합 |
| 프롬프트·AI 파싱 | LIGHT/FULL 선택, 사용자 입력, Schema, null·필수 필드, 버전, FULL 재추론 상한 |
| 모의 추출 | 실제 AI와의 경로 분리, TEST_MODE와 자동 적용 불가, 관련 예제 |
| usage·이력 | 호출별·합계 usage, 미제공 값, elapsedMs, inferenceId, 정보 노출 |
| 웹 화면 | 요청 JSON, 예제 로딩, 단위 입력, 결과·AI 제안·사용량 표시, Node 회귀 |
| 인증·설정 | 운영 기본값, 키 부재 동작, 요청 제한, 테스트 격리 |
| 평가 하네스 | 입력 해시·trialId·중복 호출 방지, 비용 예약·미측정 usage, 평가 기준·검토 이력·백업 보존 |

## 완료

영향에 맞는 기존 mock·fixture 테스트를 실행한다. 실제 AI 호출은 사용자 요청 범위와 비용 상한이 확인된 때만 수행하고 TEST_MODE 결과와 구분한다. 운영 데이터셋을 수정하거나 배포할 때는 `AGENTS.md`의 별도 허용 경계를 따른다. 문서만 변경하면 링크·경로와 코드 설명의 일치를 확인한다. 실패는 코드와 환경으로 구분하고 수정 후 필요한 범위만 재검증한다.

실제 수행한 단계는 [보고서 규칙](../../../docs/report/report-guide.md)에 따라 저장한다. 검증 실패는 변경 결함·환경·기존 문제로 구분하고 같은 원인의 실패를 무작정 반복하지 않는다. 영향 범위가 커지면 요구사항과 검증 계획을 다시 판단한다. 마지막으로 `git diff`·`git status --short`에서 사용자 변경과 범위 밖 파일 보존을 확인하고, 변경 내용·검증 결과·미검증 범위·보고서 링크를 한국어로 전달한다.
