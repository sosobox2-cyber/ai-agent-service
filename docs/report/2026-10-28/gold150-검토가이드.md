작업 목록은 저장소의 다음 파일이다. Excel에서는 UTF-8 CSV로 열고 caseId와 row를 텍스트·정수로 유지한다.

- `logs/diverse-eval-20261028/review-worklist-gold150-v42-annotated.csv`: 기존 8개 열을 보존하고 `제안 분류`, `제안 근거`를 추가한 207행
- `logs/diverse-eval-20261028/review-match-sample-gold150-v42.csv`: 일치 215행 중 고정 해시 순서로 뽑은 22행 점검 표본

현재 화면은 URL의 dataset·caseId를 해석하는 딥링크 기능이 없다. CSV 링크는 공통 평가 화면으로 연결된다. 원본 CSV에서 caseId별로 묶고, 화면의 상품 상세에서 해당 caseId와 row를 대조한다. 검색이 caseId를 지원하지 않으면 원본 사례와 화면의 상품 정보를 대조해 찾는다. 추론을 다시 실행하는 버튼은 누르지 않는다.

## 제안 분류 읽는 방법

| 제안 분류 | 의미 | 준비된 행 수 |
| --- | --- | --- |
| AI_LIKELY_CORRECT | 원문이 AI 값을 뒷받침하며 등록값과의 차이가 표현·단위 표기 잡음일 가능성이 높음 | 34 |
| REFERENCE_BROKEN | 등록값이 다른 속성·구성 수·잘못된 물리량이나 반복 단위일 가능성이 높음 | 13 |
| AI_LIKELY_WRONG | 원문이 다른 값을 명시하거나 AI가 영양성분·인원·사용기한 등을 옵션값으로 옮긴 정황이 있음 | 71 |
| UNSURE | 원문 부족, 혼합 구성, 포장 계층, 행별 대응 또는 타임아웃으로 판정 보류 | 89 |

분류 근거는 로컬 사례의 상품명·정보고시·구성 세 필드만 사용했다. 단품 옵션명, AI의 근거 문구, 기존 등록값 자체를 정답 근거로 쓰지 않았다. 원래 CSV의 `근거 문구`는 실행 당시 기록이며, 새 `제안 근거`와 구분한다. 새 근거는 세 필드에서 확인한 짧은 사실 또는 확인 불가 사유다. 상품 전체 원문은 새 CSV에 추가하지 않았다.

AI_LIKELY_CORRECT도 자동 확정하지 않는다. 예를 들어 숫자가 같은 박스·세트라도 포장당 내용물과 판매 수가 같아야 하며, 근거 없이 단위를 치환하지 않는다. REFERENCE_BROKEN도 AI 값이 옳다는 뜻이 아니다. 둘 다 틀렸을 수 있다. UNSURE 중 타임아웃 2행은 AI 제안 자체가 없으므로 모델 오답으로 판단하지 않는다.

## 상태 선택 기준

먼저 상품명·정보고시·구성에서 본품과 증정품, 낱개와 판매 포장, 선택 가능한 변형을 구분한다. 등록값·AI 값·서버 승인 여부를 별도로 보고, 마지막에 확정값을 정한다.

| 화면 상태 | 선택 기준 | 확정값 입력 |
| --- | --- | --- |
| SUCCESS | 서버가 승인한 실제 AI 결과이며 사람이 해당 행의 AI 값을 정답으로 확인함 | 서버가 그 실행의 AI 값을 자동 저장함 |
| NEEDS_FIX | AI 값이 틀렸거나 누락됐거나, AI 값은 맞지만 서버가 검토로 돌려 시스템 개선이 필요함 | 정답을 알면 직접 입력하고 근거 메모 작성; 검토 전환이 과도한 경우 AI 값과 같은 확정값 입력 |
| REFERENCE_ISSUE | 등록값이 틀렸거나 다른 속성·코드·단위 혼동이 있거나 기준이 불명확함 | 정답을 알면 교정값과 근거 메모 입력; 모르면 비워 두고 이유 명시 |

현재 서버는 승인되지 않은 결과, AI 응답이 없는 결과, 빈 AI 값, DUPLICATE 행의 SUCCESS를 허용하지 않는다. AI 제안이 맞아도 서버가 반려했다면 SUCCESS를 강제하지 말고 NEEDS_FIX와 확정값을 사용한다. 원본 기준 자체가 틀렸다면 REFERENCE_ISSUE가 우선이며, 이 상태에서도 실제 정답을 알면 확정값을 입력한다.

SUCCESS는 현재 AI 값을 그대로 확정하는 동작이다. “등록값이 맞다”는 뜻으로 누르지 않는다. 정답이 AI 값과 다르면 다른 상태를 선택한다. DUPLICATE는 복수 매핑 구조 문제이므로 사람이 값을 적어도 현재 재채점 도구는 중복 상태를 유지한다.

원문만으로 정답을 모르면 억지로 값을 만들지 않는다. 기준이 깨진 경우에만 REFERENCE_ISSUE로 남기고, 그 외 미해결은 확정값 없이 상태·메모를 남기거나 UNREVIEWED로 보류한다. 외부 페이지를 임의로 확인했다고 기록하지 않는다.

## 확정값 입력 규칙

1. 해당 caseId·row·구매옵션명과 현재 실행을 확인한다. 서버가 새 실행을 감지하면 상세를 다시 열어야 한다. 타임아웃 사례도 새 AI 실행 없이 오류로 남긴다.
2. 물리량은 원문에서 확인한 값과 차원을 유지한다. 예: `500g`, `1kg`, `30ml`, `50cm`. `30ml`를 밀도 근거 없이 `30g`으로 바꾸지 않는다. 표기에는 숫자와 단위를 한 번만 쓰고 `30mlml`, `30gg`처럼 반복하지 않는다.
3. 수량은 본품의 판매 포장 수와 포장 내 개수를 분리한다. `500ml × 4팩 × 2세트`에서 낱개 용량, 포장당 용량, 판매 수를 어떤 계약으로 기록하는지 먼저 확인한다. 개·매·캡슐·정·팩·박스·세트를 편의상 바꾸지 않는다. 증정품을 본품 수량·색상에 섞지 않는다.
4. 모델명은 모델 코드 중심으로, 색상은 본품의 실제 색상으로, 사이즈는 해당 구매옵션의 규격으로 적는다. 색상 칸에 구성 수·모델명·FREE를 넣거나, 침구 규격 칸에 프레임 외형 치수를 넣지 않는다. 구성 목록이 여러 변형을 포함하면 현재 행에 대응하는지 확인한다.
5. 하한·범위·근사 조건을 보존한다. `71g이상`, `150~250g`, `1.12kg내외`를 정확한 단일값으로 축약하지 않는다. 현재 비교기는 이런 표현의 의미적 동치를 모두 처리하지 않으므로 사람이 결정한 표현을 일관되게 사용한다.
6. 확정값을 바꿀 때는 근거 메모를 남긴다. “정보고시 색상”, “구성의 본품 3병”, “상품명의 퀸 규격”처럼 출처와 판단을 한 줄로 적는다. 전체 원문·인증정보는 메모에 복사하지 않는다.

현재 서버는 SUCCESS 외 상태에서 확정값을 새로 교정하면 메모를 요구한다. 기존 확정값이 있는 행에서 입력 칸을 비워 저장해도 이전 값이 유지될 수 있다. 정정 취소·미확정 복귀가 필요하면 UNREVIEWED 처리로 이전 검토를 제거하고 다시 기록한 뒤 화면에서 결과를 확인한다. 이는 사람의 화면 작업이며 에이전트는 수행하지 않는다.

재채점 비교기는 공백·대소문자·일부 단위 환산(kg/g/mg, l/ml, m/cm/mm)을 처리하지만 `킹`과 `킹(K)`, `24개입`과 `24매입` 등을 자동 동치로 보지 않는다. 실제로 같은 의미라고 사람이 판단한 경우 AI 값을 정답 표현으로 인정할 수 있으나, 점수를 높이려고 AI 오표기를 복사해서는 안 된다.

## 검토 순서와 예상 시간

먼저 REFERENCE_BROKEN 13행과 AI_LIKELY_CORRECT 34행을 원문과 비교해 기준 잡음을 정리한다. 이어서 AI_LIKELY_WRONG 71행을 확인하고, UNSURE 89행은 상품별로 묶어 포장 계층·다중 구성 등을 검토한다. 서버가 승인했지만 불일치한 행은 특히 우선 확인한다. 분류대로 일괄 저장하거나 자동 체크하지 않는다.

등록값과 AI 값이 같은 EXACT·EQUIVALENT 215행은 약 10%인 **22행만 표본 점검**할 것을 권고한다. 준비된 고정 표본 CSV를 사용하면 다음 검토에서도 같은 행을 확인할 수 있다. 표본에서 오류가 나오면 해당 구매옵션·상품군을 추가로 넓혀 본다. 전체 일치 행을 이미 사람이 확인한 것처럼 기록하지 않는다.

시간은 실측이 아닌 계획 추정이다. 불일치 207행에 행당 약 1~2분이면 3.5~7시간, 원문 대조·복잡한 구성·화면 이동에 1~2시간, 일치 표본 22행에 20~45분을 더해 **약 5~10시간**을 잡는다. 처음 20행의 실제 시간을 재어 보정하고 60~90분 단위로 나누어 검토한다. 반복 상품을 묶으면 단축할 수 있고 원문이 부족하면 더 걸릴 수 있다.

## 검토 완료 후 재채점 절차

현재는 사람이 검토 완료를 알리지 않아 스냅샷 내보내기·확정값 재채점·개선 후보 상위 3개 선정은 아직 수행하지 않았다. 검토를 끝낸 뒤 “gold150 사람 검토 완료”라고 알려주면 에이전트가 다음 읽기·로컬 집계만 수행한다.

```powershell
powershell -NoProfile -File scripts/export-evaluation.ps1 -BaseUrl "https://ai-agent-service-production-7624.up.railway.app" -DatasetId "74df8638-d622-498b-a242-f894e581c2e2" -OutputPath "evals/gold150-v42-reviewed-20261028.json"
node scripts/eval-metrics.cjs logs/diverse-eval-20261028 plan-gold150-v42.json --reviews evals/gold150-v42-reviewed-20261028.json
node scripts/eval-metrics.cjs logs/diverse-eval-20261028 plan-gold150-v42.json --reviews evals/gold150-v42-reviewed-20261028.json --json
```

API 키가 필요한 환경이면 스크립트의 기존 환경변수 참조를 사용하고 값은 출력하지 않는다. 위 명령은 지금 실행한 명령이 아닌 후속 절차다. 기존 스냅샷이 있으면 다른 이름으로 보존하며, 원래 등록값 기준 `metrics-gold150-v42.json`을 덮어쓰지 않고 확정값 결과는 별도 파일로 저장한다. 스냅샷은 승인된 `evals/` 아래에 저장하고 원문을 보고서에 복사하지 않는다.

스냅샷 전체 검토 수와 고정셋 150건에 해당하는 확정 행 수를 분리한다. 등록값 불일치만 집중 검토하고 일치 행을 10% 표본 점검하면 확정 행은 부분 표본이다. 현재 도구의 확정값 지표는 **확정값이 있는 행만으로 상품을 판정**하므로, 일부 행만 검토한 상품을 전체 정답이 검증된 상품으로 해석하면 안 된다. 전체 422행 중 확정·제외·미검토 행 수와 전 행 확정 상품 수를 함께 기록한다. REFERENCE_ISSUE인데 확정값이 없는 행은 재채점에서 제외되며, 미확정 행을 정답으로 간주하지 않는다.

재채점 후 [운영 평가 보고서](gold150-v42-운영평가_단계.md)에 `확정값 기준` 절을 추가한다. 확정 행 수, 상품·행의 검토 범위, 오류, 오승인율·자동승인율·정답인데 검토 전환 비율과 각 Wilson 95% 구간을 명시한다. 상품·분모가 달라지면 이전 등록값 기준 비율과 단순 전후 비교하지 않는다. **기준 교정으로 오른 일치율은 모델 개선이 아니다.**

확정값 기준으로 승인 오답 행이 많은 구매옵션 상위 3개를 정리한다. 정답인데 검토된 상품(`REVIEW_BUT_CORRECT`)만 따로 골라 validationErrors의 사유 상위 3개도 집계한다. 기본 출력의 topReviewReasons는 검토 오답 상품까지 포함하므로 그대로 후자의 상위 3개로 쓰지 않는다. 동일 상품의 반복 사유를 중복 집계할지 여부와 분모를 명시한다. 확정된 오답·과도 검토 근거가 부족하면 그 사실을 적고 3개를 억지로 채우지 않는다. 개선 후보는 제안만 하며 구현하지 않는다.

## 준비 작업 검증

AGENTS.md, 검토 저장 조건, 비교·재채점 코드, 스냅샷 내보내기 스크립트를 읽었다. 로컬 Node 일회성 집계·검증으로 원본 작업 목록 207행과 주석 CSV의 기존 8개 열을 대조해 내용 보존을 확인했다. caseId·row 조합 207개가 고유하고, 총 10개 열이며, 모든 분류가 지정된 네 가지 중 하나이고 새 근거가 한 줄임을 확인했다. 원본 근거에 있던 줄바꿈은 원래대로 보존했다.

일치 215행의 약 10%인 22행을 EXACT·EQUIVALENT 실행 기록에서 직접 뽑았다. 표본은 구매옵션 7종을 포함하며 불일치 작업 목록과 중복되지 않는다. 검증 요약은 `logs/diverse-eval-20261028/review-preparation-gold150-v42-validation.json`이다. 정적 분류 결과에는 제품 정보가 부족한 행이 포함돼 최종 정답 검증을 대신하지 못한다. 이번 작업은 로컬 자료만 읽었으며 외부 API 호출은 없었다. 소스·프롬프트·설정 변경이 없어 빌드·회귀 테스트는 하지 않았다.
