- 수행: 요구사항 → 구현 → 테스트. 실제 AI 호출 없음, 배포 안 함.
- 근거: [자동 적용 보류 정책](자동적용-보류정책과-모델명검증_단계.md). 정책의 실제 효과를 평가 예산 없이 운영 결과로 확인하기 위한 작업이다.

- 저장 위치: 기존 평가 데이터셋 형식을 재사용한다. 검토 화면, 정답 저장 도구, 지표 집계, 배포 때의 백업·복원을 그대로 쓴다.
- 표본: 자동 적용 결과 10%, 정책 보류 결과 5%
- 보관: 기한 없음. 처음에는 90일로 정했다가 2026-10-29에 바꿨다. `retention-days`를 양수로 설정하면 그 일수만 보관한다.

## 구현
- `ProductionSampleRecorder`: 평가 기능이 켜지고 파일 저장소를 쓸 때만 동작한다.
  - 실제 AI 승인 결과만 대상으로 하고, 비율에 따라 무작위로 고른다.
  - 데이터셋은 sourceHash `production-sample`로 찾는다. 배포 복원으로 ID가 바뀌어도 같은 데이터셋에 이어서 쌓인다. 없으면 새로 만든다.
  - 사례 하나에 단품 × 허용 구매옵션마다 기준 행을 만든다. 기준값은 비우고, 응답은 실행 기록으로 저장한다.
  - 기본은 지우지 않는다. 보관 기간을 설정하면 저장할 때 하루 한 번 기간이 지난 사례를 지운다.
  - 실패는 경고 로그만 남기고 응답에 영향을 주지 않는다.
- `EvaluationStore.appendCase`, `prune`: 사례를 추가하는 기능과 보관 기간 정리 기능을 추가했다. Blob 저장소는 대상이 아니다.
- `PurchaseOptionController`: 운영 `/infer` 응답 뒤에 표본 후보로 넘긴다. 평가 화면에서 실행한 결과(`EvaluationService.run`)는 대상이 아니다.
- 문서: `ai-operations.md` 10장 "운영 표본"

## 운영 사용 방법
1. 배포 후 표본이 쌓이면, 평가 화면에서 "운영 표본" 데이터셋을 연다.
2. 이번 평가와 같은 방식으로 정답을 확정한다. Claude 초안 + 애매한 행만 사람이 답한다.
3. 자동 적용 결과의 오승인율을 집계한다. 원장·계획 대신 데이터셋 스냅샷의 실행 기록을 쓴다.
   - `export-evaluation.ps1`로 "운영 표본" 데이터셋의 git-snapshot을 저장소 안에 받는다.
   - `node scripts/eval-metrics.cjs --snapshot <스냅샷.json>`. 검토된 사례만, 사례별 최신 AI 실행 기준으로 집계한다. `eval-metrics.test.cjs`에 테스트를 추가했다(Node 29개 통과).

## 미반영·위험
- 커밋·배포 전이다. 배포 절차의 백업·복원 대상에 "운영 표본" 데이터셋이 포함되는지 확인해야 한다. Codex의 기존 절차는 모든 데이터셋을 복원한다.
- 배포 직후부터 복원이 끝나기 전까지 들어온 표본은 별도의 새 데이터셋에 쌓인다.
- 운영 호출량에 따라 하루 표본 수가 정해진다. 호출량이 적으면 표본이 모이는 데 시간이 걸린다.

## 커밋·배포 준비 검증 (Codex, 2026-10-29)

사용자가 Java·Node 테스트 후 의미 단위 커밋과 기존 절차의 운영 백업·배포·복원을 승인했다. 프롬프트 버전은 `coupang-option-v45`로 유지하고 프롬프트 본문·Schema는 변경하지 않는다. `.run`, `.claude`, `~` 백업, logs는 커밋에서 제외한다.

### 영향 검토와 호환 수정

일반 추론 Controller가 기존 응답을 받은 뒤 표본 기록기를 호출한다. 추론 승인 정책과 실제 AI 입력을 바꾸거나 추가 AI 호출을 만들지 않는다. 다만 상품 요청·응답을 파일에 보관하고 백업·검토에 연결하므로 저장 실패의 격리와 복원·접근 경계를 함께 확인했다.

기존 구현에서 표본 추가 후 metadata의 상품 수가 0으로 남고, 기존 복원기와 로컬 검토 경로는 `c...` ID만 허용했다. 따라서 표본의 `pYYYYMMDD-xxxxxxxx` ID로 저장→검토→백업→복원하는 경로가 동작하지 않았다. 테스트를 먼저 추가해 **2실패·1오류**를 확인했다(`target/production-sample-before-fix.log`).

운영 표본 저장 단위에 다음 필수 호환 수정을 함께 포함한다.

- `EvaluationStore`: 추가·정리 후 상품·기준 행·단품 수를 metadata와 메모리 양쪽에 갱신한다.
- `EvaluationArchive`: 기존 ID와 정확한 표본 ID 형식만 허용하며 경로 이탈 문자열은 계속 거부한다. 표본이 모두 정리된 빈 데이터셋도 sourceHash가 `production-sample`인 경우에만 복원한다.
- `LocalEvaluationAccess`: 동일한 표본 ID의 조회·검토·실행 경로를 기존 로컬 접근 조건 안에서 허용한다. 외부 호스트·교차 출처·다른 API의 접근 제한은 유지한다.
- `ProductionSampleRecorderTest`: 상품 수 갱신, 빈 표본, 검토·실행 보존과 새 데이터셋 ID 복원 후 이어 저장하는 테스트를 추가했다. 기본 보관 기한 0(무제한)은 유지했다.
- 운영 문서의 집계 명령은 이번에 추가한 `--snapshot`으로 맞췄다.
