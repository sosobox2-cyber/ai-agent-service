# 짝지은 버전 비교와 반복 변동 기준선

- 작성일: 2026-10-31 (Asia/Seoul)
- 목적: 이미 수집된 평가 기록만으로 버전 비교의 분해능을 올린다. 실제 AI 호출은 하지 않는다.
- 변경: `scripts/eval-compare.cjs` 신규, `scripts/eval-metrics.cjs`의 깨진 경로 복구

## 배경과 요구사항

프롬프트 v42~v45는 각 버전마다 gold150을 평가하고 확정값 기준 오승인율의 **점추정 하락**을
근거로 다음 버전을 정해 왔다. 그런데 같은 버전을 두 번 돌린 결과가 그 효과와 같은 자릿수로 흔들린다.

[holdout150 반복 실행](../2026-10-29/holdout150-반복실행_단계.md) 기준, 동일 v44·동일 입력·동일 확정값:

| | 1회차 | 2회차 |
|---|---:|---:|
| 확정값 오승인율 | 17.5% [9.8–29.4] | 13.5% [6.7–25.3] |
| 판정이 바뀐 상품 | — | 14 / 116 |
| 승인↔검토 뒤집힘 | — | 9 / 150 |

버전을 바꾸지 않아도 오승인율이 4.0%p 움직인다. v43→v44의 점추정 하락폭은 10.4%p이고
Wilson 구간은 완전히 겹친다. 기존 보고서들도 매번 "개선으로 단정할 수 없음"을 적고 있다.

문제는 표본이 작다는 것만이 아니다. **모든 버전이 같은 150상품을 돌리는데도
지표는 독립 비율 두 개의 Wilson 구간으로 비교한다**(`eval-metrics.cjs`의 `wilson`, `summarize`).
독립 구간 비교는 "같은 상품이 어느 쪽에서 맞고 틀렸는지"를 쓰지 않는다.

완료 조건: 같은 사례를 짝지어 비교하고, 동일 버전 반복을 영가설 띠로 함께 제시한다.
기존 지표 정의와 출력은 바꾸지 않는다(과거 보고서 수치와의 비교 가능성 보존).

## 선행 — 깨진 경로 복구

이전 세션에서 `eval-metrics.cjs`에 `assertSameSource(planSourceHash, snapshot)` 호출만 들어가고
**함수 정의가 없는 채로 중단**돼 있었다. `--reviews` 경로가 `ReferenceError`로 죽는 상태였다.
확정값 기준 지표를 내는 바로 그 경로다.

이 결함은 JS 테스트 31개가 전부 통과하는 중에도 드러나지 않았다. `--reviews` 경로를 타는
테스트가 하나도 없었기 때문이다.

- `assertSameSource`를 정의했다. 계획의 `sourceHash`와 스냅샷 `source.sourceHash`
  (`EvaluationArchive.GitSnapshot.source`)가 다르면 중단한다. `caseId`가 가져오기 순번(`c%05d`,
  `EvaluationImporter`)이라 원본이 바뀌면 같은 번호가 다른 상품을 가리키기 때문이다.
  어느 한쪽에 해시가 없으면(운영 표본은 `sourceHash`가 상수) 대조하지 않는다.
- 해당 분기를 덮는 테스트를 `eval-metrics.test.cjs`에 추가했다.

## 구현 결정

**별도 스크립트로 분리했다.** `eval-compare.cjs`는 `eval-metrics.cjs`의
`classify`·`rescore`·`loadReviews`·`readLines`를 그대로 가져다 쓰고 판정 로직을 새로 만들지 않는다.
기존 집계 경로(`collect`·`summarize`·`render`)는 한 줄도 바꾸지 않았다.
지표 정의를 건드리면 과거 보고서와 비교할 수 없게 된다.

**McNemar 정확검정을 쓴다.** 불일치쌍 b·c에 대해 Binomial(b+c, 0.5) 양측 확률을 정확히 더한다.
카이제곱 근사는 표본이 작아 쓰지 않는다. 일치쌍은 검정에 들어가지 않는다.

**이진 결과 3개**로 환원한다: `자동 적용`(`APPROVED_*`), `AI 제안 정답`(`*_CORRECT`),
`오승인`(`FALSE_APPROVAL`). 양쪽에 모두 있고 `ERROR`·`UNSCORED`가 아닌 사례만 짝짓고,
제외된 수를 출력에 남긴다.

**해석을 출력에 강제한다.** 두 팔의 `promptVersion`이 같으면 "측정 변동이며 영가설 띠로 쓴다",
다르면 "같은 버전 반복 비교를 함께 실행해 이 불일치가 측정 변동을 넘는지 확인한다"를 출력한다.
수치만 두면 또 점추정으로 읽힌다.

## 검증

```powershell
node --test src/test/js/eval-compare.test.cjs     # 8개 통과
node --test src/test/js/*.test.cjs                # 40개 통과 (이전 31개 + 신규 9개)
node scripts/eval-compare.cjs                     # 사용법 출력, 종료코드 1
node scripts/eval-compare.cjs /tmp/x a.json b.json  # logs 밖 폴더 거부, 종료코드 1
```

McNemar 값은 손계산과 대조했다. 보고서의 실제 불일치 구조를 그대로 넣었다.

| 비교 | 불일치쌍 | p |
|---|---|---|
| v43 → v44 (버전 변경) | 13 대 4 | 0.0490 |
| v44 → v44 (동일 버전 반복) | 7 대 2 | 0.1797 |

버전 변경이 반복 변동보다 작은 p를 낸다는 것이 이 도구의 요점이며, 이를 테스트로 고정했다.
`b = c`이면 p = 1, `b = c = 0`이면 0으로 나누지 않고 p = 1을 돌려준다.

`eval-metrics.cjs`의 `git diff`를 확인해 `collect`·`summarize`·`render`·`classify`·`wilson`·
`compareValue`가 변경되지 않았음을 대조했다. 추가는 `assertSameSource`, `planSourceHash` 배선,
export 두 개뿐이다.

## 검증하지 못한 것

**실제 평가 데이터로 돌려보지 못했다.** `logs/`는 `.gitignore` 대상이라 이 작업 환경에
`logs/diverse-eval-*` 폴더가 없다. 검증은 임시 폴더의 합성 원장·실행 JSON으로만 했다.

실사용 확인은 평가 폴더가 있는 환경에서 해야 한다. 첫 확인 방법은 위 표의
13 대 4 / 7 대 2를 이 도구로 재현하는 것이다.

```powershell
node scripts/eval-compare.cjs logs/<평가폴더> plan-gold150-v43.json plan-gold150-v44b3.json --reviews <git-snapshot.json>
node scripts/eval-compare.cjs logs/<평가폴더> plan-gold150-v44b3.json plan-gold150r2-v44.json --reviews <git-snapshot.json>
```

Java 소스와 프롬프트는 변경하지 않았으므로 Maven 테스트는 실행하지 않았다.

## 자체 검토

- **중간 심각도 — 깨진 코드를 남긴 채 세션을 끝냈다.** `--reviews` 경로가 이틀간
  `ReferenceError` 상태였다. 테스트가 그 경로를 덮지 않아 31개 통과로 가려져 있었다.
  조치: 정의 복구 + 해당 분기 테스트 추가. 남은 위험: `eval-metrics.cjs`의 CLI 경로 중
  `--snapshot` 분기는 여전히 테스트가 없다.
- **이 도구는 통계적 유의성을 만들어 주지 않는다.** 짝지은 검정은 같은 데이터에서 더 많은
  정보를 쓸 뿐이다. v43→v44의 p=0.0490은 동일 버전 반복의 p=0.1797과 나란히 놓고 읽어야 하며,
  반복이 두 번뿐이라 영가설 띠 자체의 불확실성도 크다.
- **다중 비교를 보정하지 않는다.** 이진 결과 3개에 대해 각각 p를 내므로, 셋 중 하나가
  0.05 아래인 것을 단독 근거로 쓰면 안 된다.
- 평가 기준·검토 이력·백업·원장은 건드리지 않았다. 실제 AI 호출 0건, 추가 비용 $0.

## 같은 작업 트리의 선행 변경

이 보고서 범위 밖이지만 함께 미커밋 상태다.

- `scripts/eval-diverse.cjs`의 `plan` 명령이 `promptVersion: 'coupang-option-v27'`을
  하드코딩하던 것을 인자 필수로 바꿨다. 허용목록에 누락돼 있던 `coupang-option-v33`을 추가했다.
  해당 테스트 2개를 `eval-diverse.test.cjs`에 넣었다.
  실행 경로는 응답 버전을 이미 대조해 중단하므로(`execute`), 이 결함의 영향은 지표 오염이
  아니라 계획 생성 직후 중단이다.
